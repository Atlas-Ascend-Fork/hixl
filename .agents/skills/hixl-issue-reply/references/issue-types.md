# 各类型的处理重点

按实际内容选择一行，保留对本问题有用的信息。以下是处理条件，不是必须逐项向用户提问的表单。

| 类型 | 进入处理需要的关键输入 | 首响和推进重点 | 可关闭依据与复用内容 |
| --- | --- | --- | --- |
| 漏洞 | 受影响版本/范围、触发条件、影响和已有缓解信息 | 确认风险线索，核实安全报告渠道与承接；说明安全的下一步和已确认处理窗口 | 修复/缓解/公告等处置依据明确，保留适合公开的补丁、版本和验证信息；私密细节留在受控渠道 |
| 缺陷 | 复现路径、环境、预期/实际、相关日志 | 提供候选原因与判别动作，持续给定位、规避、修复及验证证据 | 已修复或给出可验证规避方案；修复提交/PR、适用版本、操作步骤和验证结果可查 |
| 需求 | 使用场景、痛点、价值、期望效果和边界 | 准确复述诉求，明确评估责任及兼容性、成本、替代路径等取舍 | 采纳/拒绝/延期及理由清楚；采纳/延期有跟踪入口与复查条件，拒绝有适用解释和可行替代（如有） |
| 文档 | 文档链接/版本、具体位置、错误与期望 | 核实文档和实现，给修订方案与承接 | 已修正，或有明确纳入修订的跟踪记录、责任与节点；保留更新链接/PR/修订说明，不能仅口头说会改 |
| 咨询 | 场景、目标、具体疑问及已尝试内容（必要时） | 直接回答，说明适用条件，给可执行示例或准确资料；多问逐项答 | 核心疑问已正确回答；保留版本范围、用法、验证方法及资料，用户仍有反证时继续处理 |
| 任务 | 目标、范围、验收条件、承接与节点 | 明确产出与依赖，更新完成情况、偏差和下一步 | 验收产出及承接清楚；关联结果、遗留事项和后续责任 |
| 审查 | 已合并 PR/commit、文件/位置、逐条意见及理由 | 逐条明确修复、解释不采纳或转交的路径与承接 | 所有意见有处置结论和依据，保留修复 PR、逐条说明和验证；仅转交不等于处置完毕 |
| 其他 | 背景、目标、现象和必要上下文 | 先澄清真实诉求，明确路径；可归类后建议调整类型 | 有明确处理结果、证据和继续跟踪入口 |
| 里程碑 | 发布/阶段目标、范围、验收项、依赖、责任和节点 | 单独保留里程碑类型，逐项更新交付与阻塞，时效沿用任务规则 | 达成项和未达成项交代清楚，未完成项有承接，关联版本/产出/后续里程碑 |

## HIXL 缺陷的最小证据选择

只补本轮判别所需的信息，优先从正文、附件和历史评论中提取：

- HIXL 的 tag/commit 或安装包版本；CANN toolkit/runtime、驱动及固件版本，以实际诊断需要为准。
- 芯片型号、操作系统/容器、进程/设备/节点拓扑，以及使用的是 HIXL、ADXL 还是 LLM-DataDist API。
- 最小调用序列与双方角色，错误首次出现时间、API/错误码、期望和实际结果、发生频率。
- 传输问题中已知的 HCCS/RDMA 路径、D2D/D2H/H2D 方向和数据规模；不知道时不要逼用户猜测。
- 必要的双端脱敏日志片段和时间窗口；解释为何需要对端证据，考虑时钟差和先后关系。

提出验证步骤时注明环境和成功/失败判据，优先使用该版本现有样例及文档入口。
构建和测试遵守仓库 `AGENTS.md`：使用 `bash build.sh`、`bash tests/run_test.sh`，先加载 CANN 环境；
没有硬件或依赖时把建议步骤与已执行结果分开，不能把分析写成复现成功。

## 特殊去向

- **疑似漏洞**：先查仓库实际安全政策和私密报告入口，不猜邮箱，不在公开评论索要利用细节、凭据或完整
  敏感日志。公开回复可说明已知影响和安全下一步；没有验证时用“疑似”，不要宣称漏洞已确认。
- **重复问题**：核查现象、版本、根因/诉求确实重叠，链接主单并说明主单如何覆盖本问题；独有信息和未解决
  部分需保留承接。“看起来类似”不够支持按重复关闭。
- **非本仓问题**：提供依赖组件证据和正确入口，说明 HIXL 侧需要继续验证什么。未确认接收前保持协调说明，
  不仅回复“找其他团队”。没有权限建单时交付可转交材料，不假装已转交。
- **无法复现**：记录复现环境、步骤、次数及与用户环境的差异，再提出判别动作；一次未复现不证明问题不存在。
- **没有回复或信息不足**：标明必要缺口，给收集办法和收到后的计划。按核实的仓库政策决定后续，不能当成已修复。
